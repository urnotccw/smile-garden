# 微笑花园：笔试交付评审

日期：2026-09-13。范围：当前本地代码、最新浏览器模拟画面、既有视觉记录及用户提供的笔试规则。本轮为检查与建议，不修改特效、不发布。建议不代表已经实现；模拟视口不等于手机真机验收。

## 结论

核心玩法已有足够的内容。下一轮应集中在人物与特效的视觉主次、第一次体验是否顺利、真实碰撞是否容易看懂，以及可复现的验收和交付证据。继续增加玩法会挤占这些工作的时间。

直播平台背景意味着：主播的表情应始终清楚，评论和礼物能读懂，普通讲话不应不断触发特效，设备需要长时间稳定工作。画面最热闹的瞬间不等于最好的设计。

## 本轮核验

- 当前规则测试 72/72 通过，包含 60% 烟花完成门槛、头顶连续碰撞、手掌接取、竖屏爱心落水转换等。
- 重跑桌面 1440×940、手机模拟视口 390×844 的浏览器验证；各 24 组花草生成，成熟组合为 7–10 株，前后根部错层与拨动命中通过；画幅切换、阈值保存通过，无 pageerror。
- 上述花园验证是受控生成的视觉场景，不是新一轮真人摄像头测试。既有模型测试也不能代替真实手机、多人识别与弱网验收。
- 检查了最新手机花园截图；烟花审美建议同时参考用户提供的真实画面及现有实现，未把历史截图当作当前所有细节的证据。

## 审美优化：保留风格，调整主次

### 1. 花草与直播 UI 的关系优先处理

最新模拟画面中，左侧亮黄、紫色花朵和白色评论发生视觉重叠；即使评论绘制在最上层，文字仍难读。建议保留现有前后两层、最多 10 株的机制，将评论区域背后的高对比花瓣错开或局部减弱；中央以低矮、低对比叶片过渡。左右各选少量主花，后排承担数量和纵深。数量上限不等于每一株都需要同样醒目。

应按完整花型的视觉边界避让，而非只看根部间距。水面星星也应为输入栏和礼物按钮保留阅读空间。纯净画面继续完整展示特效，不需要为了模拟 UI 永久删掉所有底部内容。

### 2. 烟花用清楚的轮廓表达丰富度

已有四种图案、双色配奶油高光，方向成立。接下来检查真实摄像背景下的轮廓辨识：在小屏和白墙背景仍能分清鲸鱼、星球、爱心。必要时增强关键外轮廓的粒径与连续性，减少内部填充和外围无意义闪点；避免所有粒子一起放大变成发光团。

保留用户要求的多种颜色，每朵限制主要颜色，跨朵变化。爱心、星星、雨滴、植物继续统一蜡笔材质，烟花柔光辅助轮廓，不淹没纹理。现有脸部装饰减弱逻辑应继续保留并用白衣、白墙、暗背景复核。

### 3. 强调碰撞的因果关系

验收者应直接看到“下降星光接触头顶 → 从接触点反弹为爱心”。现有代码已有连续碰撞和接触标记；下一步检查真实头部移动时是否贴合、接触是否被烟雾和其他光点掩盖。反弹后避免爱心长期聚集遮挡额头。手掌接住与水面落星同样要保持明确接触点。

### 4. 用一段完整体验评审节奏

录制真实人物的短演示：自然表情 → 微笑雨景 → 大笑烟花 → 碰头爱心 → 手掌接取 → 落水星星 → 回到微笑。检查进入、高潮、退出三段，尤其是连续说话和快速切换表情。录像用于说明，不能替代可交互 Demo。

## 细节与代码优化优先级

| 优先级 | 证据与问题 | 建议及验收方式 |
|---|---|---|
| P0 | 真机验收表均待测 | PC Chrome/Edge、iPhone Safari、Android Chrome 各完成一次全链路；记录真实失败，不以手机框代替 |
| P1 | app.js 的非错误 message 被隐藏；phone-stage 隐藏顶部状态，镜头一连接即显示“已开启” | 在现有镜头状态位置区分等待授权、准备识别、识别就绪、未检测到人脸；不恢复已删除的大段提示 UI。慢速加载和失败后重试都要可理解 |
| P1 | tracker-worker.js 每帧先运行手势，app.js 总是传 wantHand:true；人脸按约 125ms 更新 | 先测脸/手各自耗时和反馈延迟，再调度：无人手时降低手势探测频率，检测到后恢复；保证核心表情与头部更新不长期等待手势。避免无依据地一刀切降低识别频率 |
| P1 | 头部是跟踪椭圆代理，不是头发精确轮廓 | 验证刘海、帽子、侧脸、快速点头和移出重入。开发模式展示代理轮廓定位偏差；优先修坐标和时延，暂不增加高成本分割模型 |
| P2 | 烟花有自适应画质，effects.js 雨景 DPR 仍固定上限 2 | 将各层纳入统一性能预算；先降低烟雾、光晕等装饰开销，保留碰撞与主要轮廓。用真实低端设备长时数据比较 |
| P2 | effects.js visiblePlants 在绘制与拨动中重复筛选和排序 | 花园内容、画幅、尺寸变更时重算布局并缓存；先确认收益。最多 10/36 株的小规模计算不是已证实的首要瓶颈 |
| P2 | 主要浏览器验证在项目外 work/，含本机绝对工具路径 | 整理少量有效的便携浏览器回归进仓库；优先覆盖权限恢复、横竖切换、模型失败、表情切换和坐标对齐 |
| P2 | 复盘、真机表和部分文档措辞滞后 | 统一 60% 门槛、72 项测试、可调阈值和单人单手范围；在最终提交时固定版本 |

MediaPipe 的 detect/detectForVideo 为同步调用，官方建议通过 Worker 避免阻塞界面。目前 Worker 优先、限制在途帧、低分辨率采样和纹理缓存应保留。主线程回退路径更需要实测。依据：[MediaPipe Web 指南](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/web_js)。

模型和运行时体积也是首次体验的一部分。vendor 包括两种 WASM 备选文件，不能把目录总大小直接当作实际下载量。应测冷缓存请求的实际传输字节、首个人脸结果和首个手势结果耗时，再决定压缩、缓存和加载策略，不盲目删兼容文件。

### 一个需要讲准确的实现口径

当前“60%”表示每枚烟花的主体粒子完成飞行：落水、变爱心/星星、失效离场都计入，并非严格统计 60% 粒子接触地面。这个设计避免衍生爱心把降雨永久锁住，README 已说明。展示与答辩应沿用这个准确说法；若要严格接地计数，需要另外定义分母和离场行为，不能只换一句文案。

## 建议的真人验收

- 3–5 位体验者分别做自然表情、正常讲话、微笑、张嘴大笑；记录误触发和漏触发，并记录当时两个阈值，而非只验证同一个人。
- 开启授权、拒绝后恢复、设备占用、切镜头、切后台后返回、画面旋转逐项验证。
- 明亮与昏暗环境、白墙与复杂背景、眼镜与帽子、远近距离分别观察视觉与识别。
- 连续运行 5–10 分钟，记录绘制帧时间、脸/手识别频率、各自延迟、发热和内存趋势。以稳定 30fps 以上为建议目标，不用瞬时 200fps 代替稳定性证据。
- 接近实际直播负载验证；原型网页可运行并不等于已完成平台 SDK 接入或推流兼容。

## 复盘候选正文（200 字以内）

最大陷阱是把表情切换与所有粒子清空绑定，导致烟花后降雨恢复过慢。核心纠偏 Prompt：“烟花大约百分之60落地后就可以接上微笑下雨”。我将表情、每枚烟花主体飞行进度与衍生爱心分开管理；主体完成60%后放行，新烟花继续阻塞，转化和离场粒子计为完成。72项规则测试通过，真机仍待验收。

此段使用本次对话中的真实 Prompt；“真机仍待验收”必须在真正完成验收后才可更新。应由提交者确认其符合实际经历。

## 执行顺序

先修加载状态和直播安全区，再以真人反馈调识别与碰撞；随后做低端设备性能与异常恢复验收，最后统一文档并在用户恢复发布后完成线上 Demo 和 Public 源码。现有功能足够，不建议本轮继续扩张玩法或重写整套渲染引擎。
