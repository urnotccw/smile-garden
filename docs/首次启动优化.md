# 首次启动与识别准备（2026-09-13）

问题：原流程等待摄像头开启和设备枚举结束后，才启动模型；识别引擎脚本、WASM、人脸模型依次下载，Worker 随即初始化手势模型。某些浏览器设备枚举或下载卡住时，用户可能一直看到“正在准备识别”。

本次调整：

- 点击开启时，摄像头授权和识别资源准备并行进行。摄像头仍只在用户点击后请求；视频帧只在本机处理。
- 设备列表后台枚举；即使枚举不返回，也不会阻塞人脸识别。
- 三个必要文件并行下载，通过内存模型和 Blob URL 交给已有 MediaPipe 运行时；手势初始化复用同一份运行时文件，不再额外请求一次 WASM。保留现有模型精度和资源。
- 首个人脸结果发送后，延后 1 秒准备手势，让首批降雨先响应。
- 检查 Worker 的真实 WebGL 能力；只有 API 名称存在但缺少实现时，立即进入主线程 CPU 兼容路径。
- 实际下载字节数显示在已有状态位置；12 秒无下载进展、单个资源下载超过 45 秒，或模型初始化超过 18 秒时结束等待并允许重试。下载失败不再盲目换线程重复同一次请求。迟到的初始化结果会被关闭。
- 没有新增微信提示或跳转浏览器界面。

## 对照测量

同一本机 Chromium、真实内置模型、空白合成视频；模拟授权等待 1200ms、设备枚举等待 1800ms、每个 vendor 请求延迟 200ms。该测量只比较依赖顺序，不代表手机真实网络或微信运行速度。

| 项目 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 点击至首个人脸推理结果（空白画面） | 4677ms | 1638ms |
| 识别库请求启动 | 点击后 3263ms | 点击后 223ms |
| WASM 下载开始 | 点击后 3732ms | 点击后 444ms |
| 人脸模型下载开始 | 点击后 4053ms | 点击后 444ms |

首个人脸推理结果不是“识别人脸成功”；测量输入为空白画布。真人微笑仍需模型识别和表情确认，不使用自动降雨伪装识别完成。

## 验证范围

93 项规则测试通过。浏览器检查通过 Worker / 主线程真实模型初始化、权限拒绝后恢复、布局与现有表情时序；新增 `npm run test:startup` 验证：下载卡住会超时、重新开启后成功恢复；Worker 缺少 WebGL 时自动使用主线程；设备枚举永不返回仍能完成人脸和手势推理。静态构建通过。

实际微信内置浏览器、真人摄像头与移动网络仍需真机确认；上述浏览器验证在桌面 Chromium 使用合成视频，不能据此声称已完成微信真机验收。
